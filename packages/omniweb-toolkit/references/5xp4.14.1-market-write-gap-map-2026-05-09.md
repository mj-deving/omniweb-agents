# 5xp4.14.1 — market-write gap map (2026-05-09)

## Verdict

The lower substrate for market writes is already real.

What exists today:
- live fixed-price and higher-lower write primitives already exist in the substrate (`placeBet`, `placeHL`, `registerBet`, `registerHL`)
- the production-host proof surface for both paths already exists and has an honest maintained record (`references/market-write-sweep-2026-04-17.md`, `scripts/probe-market-writes.ts`)
- the shared intent seam already knows that `bet` belongs to the `market_write` execution family

What does **not** exist yet:
- no shared executor path for `market_write`
- no market-write verification/result envelope alongside publish/reply/react/tip
- no bet-specific request validation in the resolver
- no honest runtime capability flip from placeholder to executable

So `5xp4.14.2` is **not** blocked by missing substrate primitives.
It is blocked by the missing middle-layer execution/verification contract.

## Scope

This audit is about the first shared-seam market-write slice only:
- fixed-price bets via `placeBet`
- higher-lower bets via `placeHL`
- their registration, memo, readiness, and readback truth

It is **not** about:
- Eth binary bets
- sports or commodity expansion
- changing live spend sizing beyond what the current production host has already proven
- replacing the maintained operator scripts with a fully different strategy flow

## Current substrate truth

### 1. Operator-facing write surface already exists

`packages/omniweb-toolkit/src/hive.ts` already exposes:
- `placeBet(asset, predictedPrice, { horizon })`
- `placeHL(asset, direction, { amount?, horizon })`
- `registerBet(txHash, asset, predictedPrice, { horizon })`
- `registerHL(txHash, asset, direction, { horizon })`

Those map directly into the lower primitives under `src/toolkit/primitives/actions.ts`.

### 2. The lower primitives already perform the real choreography

#### Fixed-price path

`src/toolkit/primitives/actions.ts#placeBet()` already does all of this:
1. normalize `asset`, `predictedPrice`, and `horizon`
2. build memo `HIVE_BET:<asset>:<predictedPrice>:<horizon>`
3. resolve the pool address from the API
4. fail closed if tx simulation rejects the spend
5. transfer exactly `5 DEM`
6. register the bet through `apiClient.registerBet()`
7. return `{ txHash, memo, amount, registered }`

#### Higher-lower path

`src/toolkit/primitives/actions.ts#placeHL()` already does all of this:
1. normalize `asset`, `direction`, and `horizon`
2. build memo `HIVE_HL:<asset>:<direction>:<horizon>`
3. resolve the higher-lower pool address from the API
4. enforce the current live contract that the amount must be exactly `5 DEM`
5. transfer `5 DEM`
6. register the bet through `apiClient.registerHigherLowerBet()`
7. return `{ txHash, memo, amount, registered }`

### 3. The memo contract is explicit and narrow

`src/toolkit/supercolony/bet-memos.ts` is the current source of truth for live market-write memos:
- fixed-price: `HIVE_BET:<asset>:<predictedPrice>:<horizon>`
- higher-lower: `HIVE_HL:<asset>:<direction>:<horizon>`
- allowed horizons: `10m | 30m | 4h | 24h`
- higher-lower directions normalize to uppercase `HIGHER | LOWER`

That memo contract is already narrower and more operationally useful than the old generic vote/bet codec.

### 4. The proof surface is already maintained

Current maintained proof artifacts:
- `references/market-write-sweep-2026-04-17.md`
- `scripts/probe-market-writes.ts`
- `scripts/check-market-action-bet.ts`
- `tests/packages/market-write-proof.test.ts`

These already prove the important operational facts:
- fixed-price live write works on the production host
- higher-lower live write works on the production host
- higher-lower had to be narrowed to exact `5 DEM`
- pool readback is stronger than immediate balance-delta readback for market writes

## Memo and choreography findings

## A. Fixed-price market-write choreography

The current honest choreography is:

1. choose a candidate from live oracle + pool state
2. compute a predicted close price
3. encode `HIVE_BET:<asset>:<predictedPrice>:<horizon>`
4. resolve the pool address
5. simulate the spend
6. transfer `5 DEM`
7. register the tx hash against the market API
8. confirm through pool readback
9. optionally publish a separate attested `ACTION` post describing the trade

Important consequence:
- the **bet write** and the **social publish about the bet** are already two separate actions
- the shared seam should keep them separable instead of pretending one action magically does both

## B. Higher-lower choreography

The current honest choreography is:

1. choose a candidate from live oracle + active higher-lower pools
2. encode `HIVE_HL:<asset>:<direction>:<horizon>`
3. resolve the pool address
4. enforce exact `5 DEM`
5. transfer `5 DEM`
6. register the tx hash through the higher-lower API
7. confirm through pool readback

Important consequence:
- higher-lower has a stricter live contract than the old abstract “bet amount” story
- the shared seam must expose that truth honestly instead of implying arbitrary sizing already works

## C. Naming collision worth keeping in mind

`src/toolkit/colony/vote-bet-codec.ts` also uses `HIVE_BET`, but for a different older payload shape (`direction`, `confidence`, `amount`, `expiry`) attached to a `VOTE`-style post.

That is **not** the same contract as the current live transfer memo path.

So `5xp4.14.2` should treat the live market-write seam as grounded in:
- `bet-memos.ts`
- `primitives/actions.ts`
- current proof scripts

…and avoid re-coupling it to the older generic vote-post codec by accident.

## Current shared-seam state

### What the resolver already knows

The current resolver stack already captures some correct intent-boundary truth:
- `bet` maps to `market_write` as an execution-path family
- runtime readiness marks `bet` as `requiresWallet: true` and `requiresMarketContext: true`
- runtime capability still marks `bet` as `executable: false` / `unsupported`
- non-bet action families already flow through a normalized request -> resolution -> execution -> verification path

### What still breaks at the seam

Even with that scaffolding, the bet path is still incomplete in the middle layer:

1. `resolveActionRequest()` still forces `bet` to `action_family_not_implemented`
2. `executeResolvedIntent()` has no `market_write` branch
3. `MinimalCycleStatus` has no successful market-write status
4. `toMinimalCycleStatus()` would currently collapse an executed bet into `failed`
5. the execution result union has no market-write verification type
6. the ledger/reporting shape has no first-class market-write verification payload

That is the real center of gravity for `5xp4.14.2`.

## Verification truth

## Primary verification surfaces

### Higher-lower

The maintained proof logic in `scripts/_market-write-shared.ts` treats higher-lower readback as satisfied when any of these become true:
- the side-specific count increases (`higherCount` or `lowerCount`)
- the side-specific total DEM increases by the spent amount
- the pool `totalDem` increases by the spent amount

This is the right verification family for the shared executor too.

### Fixed-price

The maintained proof logic treats fixed-price readback as satisfied when any of these become true:
- `totalBets` increases
- `totalDem` increases
- the new tx hash appears in the returned `bets[]`

Again, this should become the shared executor verification truth.

## Secondary / weaker surfaces

### Immediate balance delta

The live proof note explicitly says `getBalance()` did **not** reflect an immediate spend delta during successful market-write probes.

So balance readback should be considered:
- useful diagnostic context
- not the primary success criterion

### Registration replay

`check-write-surface-sweep.ts` currently uses `registerBet()` / `registerHL()` replay as a secondary proving step.
That is useful for diagnostics and launch proof, but the shared executor should treat the first-class success path as:
- transfer + registration succeeds
- pool readback confirms the write

## Gap map for 5xp4.14.2

| Layer | Current truth | Gap to close | Recommendation |
| --- | --- | --- | --- |
| Request contract | `bet` intent exists; current audit branch also preserves `marketKind`, `horizon`, `predictedPrice`, and `direction` through the seam | no bet-specific required-field validation yet | require `asset` + `horizon`, then exactly one of `predictedPrice` or `direction` depending on `marketKind` |
| Capability/readiness | `bet` is declared but still an architectural placeholder | capability cannot honestly flip yet | keep `unsupported` until executor + verification land |
| Executor | lower substrate is live, but shared executor has no `market_write` branch | no execution path | add `executeMarketWriteIntent()` under `action-executor.ts` or a dedicated helper |
| Verification | proof helpers already exist in scripts | no shared market verification type | add a normalized bet verification payload using pool snapshots and tx hash visibility |
| Result envelope | publish/reply/react/tip already have explicit result shapes | market write has none | extend `ResolvedIntentExecutionResult` and `MinimalExecutionOutcome` honestly |
| Cycle status | publish/reply/react/tip have success states | no market-write success state | add a dedicated success status (`betted` or `market_written`) instead of overloading `failed` |
| Action semantics | bet execution and ACTION publish are separate today | easy to blur them together | keep bet and publish separate; optionally compose them at policy level later |
| Live contract | fixed-price is effectively fixed at `5 DEM`; HL is exactly `5 DEM` | request layer could imply flexible sizing | encode current spend truth explicitly and postpone variable sizing claims |
| Surface scope | Eth binary exists only as partial registration surface and is excluded from maintained proof | tempting to widen PR6 too far | keep first seam slice to fixed-price + higher-lower only |

## Recommended 5xp4.14.2 shape

The smallest honest implementation slice is:

1. **Finalize the bet request contract**
   - require `asset` and `horizon`
   - require `marketKind: "fixed_price" | "higher_lower"`
   - for `fixed_price`, require `predictedPrice`
   - for `higher_lower`, require `direction`
   - treat `amount` as optional metadata now, but normalize execution to the proven live contract

2. **Add a market-write executor**
   - `fixed_price` -> call `omni.colony.placeBet()`
   - `higher_lower` -> call `omni.colony.placeHL()`
   - capture `txHash`, `memo`, `amount`, and registration truth

3. **Lift the proof-helper readback logic into shared verification**
   - reuse the same pool-delta conditions already maintained in `_market-write-shared.ts`
   - make pool readback the primary verification path

4. **Extend execution/result types honestly**
   - add a market-write verification union member
   - add a success cycle status for market writes
   - make reporting/ledger summaries able to show market verification path and spend

5. **Only then flip runtime capability for bet**
   - not before
   - this should remain a truthful postcondition of implementation, not a speculative claim

## Recommended non-goals for the first implementation pass

Do **not** fold these into the first 5xp4.14.2 slice:
- Eth binary send-path support
- sports/commodity market-write unification
- arbitrary higher-lower amount sizing
- automatic bundled ACTION post publish as part of the same executor action
- redesigning the old `vote-bet-codec.ts` surface
