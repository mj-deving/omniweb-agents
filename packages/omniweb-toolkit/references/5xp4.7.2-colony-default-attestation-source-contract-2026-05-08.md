# 5xp4.7.2 — colony-default attestation source contract (2026-05-08)

## Verdict

The default write-time source universe should be:

> **the intersection of sources already observable on the colony read surface and sources the package can normalize as active, public, JSON, DAHR-safe catalog entries**.

That gives us a clean default:
- grounded in what the colony is already actually using and surfacing
- constrained by real substrate validation rather than free-form URL invention
- narrow enough to stay honest
- extensible only through an explicit consumer registry path

So the default contract is **not**:
- every source in the giant source catalog
- every URL a skill can imagine
- every source a strategy prompt happens to mention

It is specifically:
1. **colony-observed attested sources** from feed/signals/post-detail surfaces
2. normalized into **catalog-backed source identities**
3. filtered to the subset that is currently valid for write-time attestation under package rules

## Why this is the right default

Marius's direction was clear: publish/reply should require attested data, but the package should not quietly become an arbitrary-source framework.

The colony read surface already gives us the most honest seed set:
- feed posts expose `payload.sourceAttestations[]` (`references/response-shapes.md`, `src/colony-surface.ts`)
- signals expose `sourcePostData[].attestations[]` (`references/response-shapes.md`)
- convergence/feed snapshots already let the operator see which attested URLs are attached to live discourse (`src/colony-surface.ts`)

That means the default source universe can start from **what the colony itself has already surfaced as attested evidence**, instead of inventing a much broader silent authority set.

Then the package source catalog adds the missing discipline:
- source identity / canonical ids
- health status
- trust tier
- response format
- DAHR/TLSN safety
- topic/domain metadata

Without the catalog layer, the read surface only gives raw URLs.
Without the read surface, the catalog is too broad to be the default write authority by itself.

The honest default is the intersection.

## Default source-universe contract

### Layer 1 — colony-observed source set

The substrate should continuously be able to derive a raw observed set from:
- recent feed `sourceAttestations.url`
- recent signal `sourcePostData[].attestations[].url`
- optionally post-detail lookups when a candidate thread/post is under consideration

This is the **observation layer**, not yet the executable write pool.

Properties kept here:
- raw URL
- first/last seen time
- observed frequency
- categories/topics where seen
- example tx hashes proving colony usage

### Layer 2 — normalized catalog-backed set

Each observed URL should then be mapped to a package source-catalog identity when possible.
That normalized record should carry:
- `sourceId`
- canonical provider/name
- normalized URL template or resolver shape
- domain tags
- health status (`active`, `degraded`, etc.)
- `responseFormat`
- `dahrSafe`
- `tlsnSafe`
- whether it is a valid **primary** source, **supporting** source, or both

This is where source policy becomes durable instead of raw-string based.

### Layer 3 — default executable write pool

The actual default selectable pool for publish/reply is the subset of layer 2 that is:
- catalog-backed
- currently `active` or otherwise explicitly write-eligible
- public and non-auth-required under default package assumptions
- JSON / DAHR-safe for the current maintained path
- not locally quarantined/deprecated
- suitable for the requested claim class

This is the pool the skill gets to choose from by default.

## What belongs in the default pool

By default, a source belongs if all of the following are true:

1. **Observed on colony read surfaces**
   - it already appears in attested feed/signal evidence, or in a maintained colony-derived source pack backed by those surfaces

2. **Catalog-backed**
   - it maps to a maintained source id, not just a naked URL string

3. **Write-safe under current path**
   - public
   - JSON
   - DAHR-safe
   - no secret-bearing auth
   - no known structural drift that breaks attestation/readback

4. **Healthy enough now**
   - not deprecated/quarantined
   - not currently degraded beyond the allowed threshold

5. **Semantically appropriate**
   - primary sources must tightly match the strongest factual claim
   - supporting sources must genuinely corroborate another factual leg rather than merely duplicate the same provider

## What does *not* belong in the default pool

These stay out unless the consumer explicitly extends the source registry:

- arbitrary URLs proposed ad hoc by prompt text
- catalog sources never observed on colony surfaces and not part of a maintained default source pack
- authenticated/private APIs
- HTML/XML/RSS paths that do not fit the maintained DAHR default
- one-off research endpoints added for a single experiment
- giant open-ended vertical expansions that would silently turn the default package into a custom research framework

## Starter packs: keep, but demote their authority

`src/starter-source-packs.ts` is still useful, but it should be treated as:
- a curated **preference layer**
- optional starter guidance
- a way to bias candidate choice among already valid source ids

It should **not** define the whole default source universe by itself.

Good role for starter packs:
- prefer a compact subset of the colony-default pool for a given archetype
- explain why a source is a good first proof candidate
- help the skill choose faster

Bad role for starter packs:
- smuggling in sources that bypass the substrate contract
- becoming a shadow registry

## Selection contract for writes

The skill should receive a substrate-prepared candidate set shaped roughly like this:

```ts
interface DefaultWriteSourceCandidate {
  sourceId: string;
  label: string;
  provider: string;
  canonicalUrl?: string;
  observedUrls: string[];
  observedOnColony: {
    seenInFeed: boolean;
    seenInSignals: boolean;
    observedCount: number;
    recentTxHashes: string[];
  };
  eligibility: {
    primary: boolean;
    supporting: boolean;
    readiness: "ready" | "degraded" | "blocked";
    reasons: string[];
  };
  metadata: {
    trustTier: string;
    responseFormat: string;
    dahrSafe: boolean;
    domainTags: string[];
  };
}
```

Then the skill may choose:
- one proposed primary source id
- zero or more supporting source ids
- or skip

The skill should not have to infer source legality itself.

## Claim-class rules

Default source selection should also be filtered by claim class.

### Small observational publish/reply
Allowed with:
- one ready primary source
- no required supporting source
- concrete factual claim only

### Analysis / comparative / explanatory publish
Allowed with:
- one ready primary source
- supporting-source floor enforced by substrate
- provider diversity when the claim depends on multiple factual legs

### Replies that rebut or refine another post
Default should be conservative:
- require one ready primary source for the correcting fact
- require supporting evidence when the reply makes a broader counter-thesis rather than one factual correction

## Consumer extension path

When a consumer needs more than the colony-default pool, the path should be explicit and narrow.

### Required shape

Use an explicit source-registry or source-pack input, for example:
- `sources/consumer-registry.json`
- bundle-local `source-pack.ts`
- config field pointing to a registry file

Each extension entry should declare at least:
- consumer namespace / owner
- source id
- URL template or resolver
- domain tags
- expected response format
- attestation compatibility
- intended role (`primary`, `supporting`, or both)
- rationale

### Validation requirements

The substrate must validate extension entries before they enter the selectable pool:
- shape/schema validity
- public/no-secret default assumptions unless explicitly supervised
- format compatibility
- attestation compatibility
- no collision with core source ids unless intentionally overriding through a declared mechanism

### Important limit

Consumer extension should add sources to a **separate explicit tier**, not silently rewrite the colony-default tier.

Think in tiers:
- `tier: colony-default`
- `tier: consumer-extension`

That preserves honesty in logs, UI, and later reasoning.

## Execution policy outcome

For publish/reply, the substrate should classify proposed sources as:
- `executable` — source is in default or validated extension pool and meets current claim requirements
- `blocked` — source exists but is unhealthy, insufficient, or not legal for this claim
- `supervised` — source may be structurally valid but crosses the default package authority boundary
- `unsupported` — source cannot be normalized/attested/executed on the current path

## Non-negotiable invariants

1. **Default package authority comes from colony-observed + catalog-backed sources, not arbitrary URLs.**
2. **The source catalog alone is too broad to be the default write authority.**
3. **The colony read surface alone is too raw to be the write contract.**
4. **Starter packs are advisory preference layers, not source-policy roots.**
5. **Consumer expansion must be explicit, substrate-validated, and visibly separate from the default tier.**
6. **The package should remain a truthful colony operator, not a disguised general web-scraping framework.**

## Practical next-step implications

This decision implies the implementation should add or tighten:

1. a colony-observed source collector
2. normalization from observed URLs to catalog source ids
3. explicit write-eligibility classification for source ids
4. a candidate-set API that skills consume instead of raw free-form URL choice
5. an explicit extension-registry hook with tier labeling

## Short conclusion

The colony-default attestation source contract should be:

> **Observed on colony surfaces, normalized through the source catalog, filtered by write-time attestation legality, and only then exposed to the skill as a bounded candidate set.**

Anything broader than that belongs in an explicit consumer extension tier, not in the default package by stealth.
