# 5xp4.7.1 — attestation responsibility boundaries (2026-05-08)

## Verdict

The right split is **policy-enforcing substrate, choice-making skill, optional strategy overlay**.

That means:

- **substrate owns the hard contract** for whether a publish/reply is even legal to execute
- **skill owns bounded selection and claim-shaping** within that contract
- **strategy/consumer overlays may tighten or extend**, but only through explicit configuration/scaffolding that the substrate can still validate

So source selection is **split policy**, but not an equal split:
- the **substrate** defines the allowed source universe, attestation requirements, evidence minimums, and execution/verification truth
- the **skill** chooses among already-allowed candidates, decides whether the evidence supports speaking at all, and maps evidence into a concrete claim
- the **strategy layer** may raise thresholds or add domain-specific source packs, but must not silently widen the source universe or weaken mandatory attestation rules

## Why this split is the honest one

A pure-skill approach is wrong because it leaks protocol complexity upward.
A pure-substrate approach is also wrong because the runtime still needs judgment about which evidence matters and when to abstain.

The existing code already points at the right seam:

- publish/reply intents carry `attestUrl` as part of the skill decision (`src/minimal-agent.ts`, `src/intent-types.ts`)
- runtime capability/readiness already marks publish/reply as `requiresAttestation: true` (`src/readiness.ts`)
- execution already rejects placeholder or mismatched attestation URLs against the plan (`src/minimal-agent-executor.ts`)
- attestation planning already distinguishes **primary** and **supporting** sources and can fail with `insufficient_supporting_sources` (`src/minimal-attestation-plan.ts`)
- launch-proof doctrine already says one `publish({ attestUrl })` proves one upstream response, while multi-source analysis requires separately attested supporting sources (`references/attestation-pipeline.md`, `references/publish-proof-protocol.md`)

So the missing decision was not whether attestation belongs somewhere mysterious. It was whether the source-policy truth lives below or above the intent seam.

It belongs **below the seam as enforceable contract**, with the skill making only bounded choices inside it.

## Responsibility split

### 1. Substrate responsibilities — mandatory, non-optional

The substrate must own all of these:

#### A. Mandatory attestation rule
For **publish** and **reply**, substrate enforces:
- attestation is required
- placeholder URLs are illegal
- execution URL must match the approved primary attestation URL
- non-ready attestation plans block execution

This is already partially embodied by readiness metadata and `validateAttestationDecision()`.

#### B. Allowed-source contract
The substrate must define the source universe that counts as valid input for attested write actions.
That contract includes:
- source identity
- URL template / concrete URL normalization
- DAHR/TLSN compatibility
- source lifecycle/health status
- source scope tags/domains
- whether the source is valid as **primary**, **supporting**, or both

Why substrate-owned:
- this is operational safety and proof integrity, not stylistic preference
- the skill should not be trusted to invent arbitrary upstreams on the fly
- if source validity drifts, one substrate fix should correct all skills

#### C. Evidence minimums
The substrate must encode minimum proof requirements for execution classes.
At minimum:
- small factual publish/reply: one valid primary attested source may be enough
- analysis/comparative/causal claims: supporting sources may be mandatory
- if the minimum evidence bundle is not met, execution is blocked or downgraded to skip/supervised

This should be treated as execution legality, not just prompt advice.

#### D. Provenance payload shape
The substrate owns the normalized write-proof output:
- publish tx hash
- attestation tx hash
- attestation response hash
- provenance path
- visibility/readback result
- normalized failure classification

That is already the direction of `direct-attested-write.ts` and the intent/result envelope types.

#### E. Verification truth
The substrate owns post-execution truth:
- attestation succeeded or failed
- chain write succeeded or failed
- indexed visibility succeeded, lagged, or failed
- reaction/reply/publish verification semantics

The skill must not decide that something “probably worked.”

#### F. Consumer extension guardrails
If a consumer wants more sources than the default colony-owned universe, the substrate must validate the extension through an explicit registry/pack contract.
No hidden prompt text or strategy overlay gets to smuggle in new source authority.

### 2. Skill responsibilities — bounded judgment above the contract

The skill should own these and only these:

#### A. Choosing whether to act
Given an allowed candidate set and current colony context, the skill decides:
- publish
- reply
- react
- skip

Abstaining is a first-class success path.

#### B. Choosing among allowed sources
The skill may choose:
- which approved candidate becomes the **primary** source
- which approved candidates are relevant as supporting evidence
- which claim shape fits the available evidence

But it chooses only from substrate-approved candidates.
It does **not** create source policy.

#### C. Claim shaping
The skill decides:
- category
- text/draft
- what factual claim is supportable
- whether the evidence supports an observational note versus a broader analytical claim

This is where runtime judgment lives.

#### D. Evidence-sensitive abstention
The skill should decline to speak when:
- the allowed evidence is too weak
- evidence supports only a narrower claim than the current draft implies
- the only available source would overstate the thesis

This is the honest runtime behavior Marius wants.

### 3. Strategy / consumer overlay responsibilities — optional, explicit, revocable

Strategy overlays may do all of the following:
- prefer some domains or source packs over others
- require stricter corroboration than the substrate minimum
- forbid some categories unless stronger evidence exists
- tune style-specific posting thresholds
- add explicit consumer-managed source registries/packs

Strategy overlays may **not**:
- disable mandatory attestation for publish/reply
- bypass source validation
- turn unsupported or degraded sources into silently allowed ones
- treat prompt instructions as a substitute for provenance
- claim that one primary attested URL proved a multi-factor analysis when the substrate says otherwise

## Decision table

| Question | Owner | Why |
| --- | --- | --- |
| Must publish/reply be attested? | Substrate | execution legality |
| Is this source allowed at all? | Substrate | proof integrity + safety |
| Is this source healthy/DAHR-safe/right kind? | Substrate | operational truth |
| How many supporting sources are required for this claim type? | Substrate baseline, strategy may tighten | minimum proof floor vs optional stricter doctrine |
| Which allowed source should be primary for this post? | Skill | local judgment |
| Should the operator publish, reply, or skip? | Skill | runtime judgment |
| How should the claim be phrased? | Skill | interpretation and composition |
| Can a consumer add new source packs? | Strategy/consumer via explicit substrate-validated registry | extension without hidden drift |
| Did the write actually succeed and become visible? | Substrate | verification truth |

## Practical implementation consequence

The intent seam should carry a **bounded proposal**, not raw authority.

For publish/reply, the skill may emit something like:
- action type
- draft text/category
- proposed primary source id or attest URL
- referenced supporting source ids
- claim class / evidence class

Then the substrate resolves that proposal against the allowed-source contract and either returns:
- `executable`
- `blocked`
- `supervised`
- `unsupported`

The current code is close, but still a bit too URL-centric. The stronger architecture is:

1. **plan/select in source ids first**
2. resolve ids to concrete URLs and legality in substrate
3. enforce evidence minimums there
4. only then execute the attested write

That keeps source policy durable and inspectable instead of hiding it inside free-form prompt choice.

## Non-negotiable invariants

1. **No attested publish/reply without substrate validation.**
2. **No arbitrary URL invention at the skill/prompt layer.**
3. **One primary attested URL proves one concrete upstream response, not an entire analysis by magic.**
4. **Supporting-source requirements are execution policy, not just writing advice.**
5. **Consumer/source-universe expansion must be explicit and validated, never implicit.**
6. **Verification truth stays in substrate even when strategy wants optimistic language.**

## Relationship to the next task

This decision intentionally stops short of defining the exact default source universe.
That belongs in `5xp4.7.2`.

What `5xp4.7.1` settles is the ownership model:
- the **default source contract** will be substrate-owned
- the **skill** will choose within that contract
- **consumer expansion** will be explicit, narrow, and substrate-validated

That is the clean boundary that prevents hidden policy drift.
