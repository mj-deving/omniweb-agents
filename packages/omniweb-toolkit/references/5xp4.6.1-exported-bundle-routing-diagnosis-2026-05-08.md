# 5xp4.6.1 — exported bundle routing diagnosis (2026-05-08)

## Verdict

**Root cause split identified.**

The exported colony-operator bundle is **not** broken as a workspace.
The real failure is that different OpenClaw entry paths resolve workspace differently:

1. **cwd alone does not activate an arbitrary workspace** for `skills check`, `skills info`, or `agent --local`
2. **a real `agents.defaults.workspace` config switch does activate the bundle for embedded `--local` runs**
3. **gateway-backed `openclaw agent` stays on the already-running main workspace until the gateway is restarted**

So the blocker is **not** “bundle takeover impossible.”
It is a combination of:
- CLI behavior that targets the current/default agent rather than raw cwd workspace
- gateway/runtime state staying pinned to the pre-restart main workspace

## Clean evidence matrix

### A. Bundle directory by itself does nothing
Working directory:
`/home/openclaw/.openclaw/workspace/local/omniweb-agents/packages/omniweb-toolkit/agents/openclaw/colony-operator`

Commands:
```bash
openclaw skills check --json
openclaw skills info omniweb-colony-operator --json
openclaw agent --local --session-id 5xp4-6-1-cwd-local --message "Identify the active workspace and active OmniWeb skill for this run. Return dry-run only." --json --timeout 180
```

Observed:
- `skills check --json` still reported:
  - `agentId: main`
  - `workspaceDir: /home/openclaw/.openclaw/workspace`
- `skills info omniweb-colony-operator --json` returned:
  ```json
  { "error": "not found", "skill": "omniweb-colony-operator" }
  ```
- `agent --local` still ran on:
  - workspace: `/home/openclaw/.openclaw/workspace`
  - skill: `omniweb-general-purpose-agent-maintainer`

Interpretation:
**raw cwd is not enough** to make OpenClaw treat this exported bundle as the active workspace.

## B. A real config switch activates the bundle for the main agent
Temporary reversible config change:
```bash
openclaw config set agents.defaults.workspace "\"/home/openclaw/.openclaw/workspace/local/omniweb-agents/packages/omniweb-toolkit/agents/openclaw/colony-operator\"" --strict-json
openclaw skills check --agent main --json
```

Observed:
- config acknowledged the change and printed: `Updated agents.defaults.workspace. Restart the gateway to apply.`
- `config get agents.defaults.workspace` returned the bundle path
- `skills check --agent main --json` then reported:
  - `agentId: main`
  - `workspaceDir: /home/openclaw/.openclaw/workspace/local/omniweb-agents/packages/omniweb-toolkit/agents/openclaw/colony-operator`
- the skill inventory now included `omniweb-colony-operator` instead of `omniweb-general-purpose-agent-maintainer`

Interpretation:
The bundle workspace itself is valid and OpenClaw **can** resolve it for the main agent when the config actually points there.

## C. Embedded local path honors the live config change
With the config still temporarily switched:
```bash
openclaw agent --local --session-id 5xp4-6-1-local-config-switch --message "Identify the active workspace and active OmniWeb skill for this run. Return dry-run only." --json --timeout 180
```

Observed from `systemPromptReport`:
- `workspaceDir: /home/openclaw/.openclaw/workspace/local/omniweb-agents/packages/omniweb-toolkit/agents/openclaw/colony-operator`
- injected files came from the bundle workspace
- returned skill: `omniweb-colony-operator`

Interpretation:
**embedded local execution is capable of honest bundle takeover** once the main agent config points at the bundle.

## D. Gateway-backed agent path stays pinned without restart
Still with the config temporarily switched, but **without** restarting the gateway:
```bash
openclaw agent --session-id 5xp4-6-1-gateway-no-restart --message "Identify the active workspace and active OmniWeb skill for this run. Return dry-run only." --json --timeout 180
```

Observed from `systemPromptReport`:
- `workspaceDir: /home/openclaw/.openclaw/workspace`
- injected files still came from the Gregor workspace
- returned skill: `omniweb-general-purpose-agent-maintainer`

Interpretation:
The gateway-backed path remained pinned to the pre-existing main workspace even after config mutation.
The CLI warning was truthful: **restart is required for gateway-backed runs to pick up the new workspace**.

## Source-level support

Relevant OpenClaw source confirms the behavior split:

### Agent workspace resolution
`dist/agent-scope-B6RIBoEj.js`
```js
function resolveAgentWorkspaceDir(cfg, agentId, env = process.env) {
  const configured = resolveAgentConfig(cfg, id)?.workspace?.trim();
  if (configured) return ...
  const fallback = cfg.agents?.defaults?.workspace?.trim();
  if (id === defaultAgentId) {
    if (fallback) return ...
  }
}
```
This shows the main agent workspace comes from agent config first, then `agents.defaults.workspace`.

### Agent command runtime handoff
`dist/agent-command-DEmhTrQM.js`
```js
const workspaceDirRaw = normalizedSpawned.workspaceDir ?? resolveAgentWorkspaceDir(cfg, sessionAgentId);
const workspaceDir = (await ensureAgentWorkspace({ dir: workspaceDirRaw, ... })).dir;
```
This shows agent execution uses the resolved session agent workspace, not an arbitrary cwd.

### Skills CLI targeting model
`dist/skills-cli-YhpqDxad.js`
```js
.option("--agent <id>", "Target agent workspace (defaults to cwd-inferred, then default agent)")
```
This matches the observed result that running from the bundle directory alone did not activate that workspace.

## Honest conclusion

The root cause is **not** provider auth, bundle packaging, or a broken colony-operator workspace.

The real diagnosis is:
- **workspace selection:** valid when changed through `agents.defaults.workspace`
- **bundle activation:** works for embedded `--local` once config points at the bundle
- **agent routing / session binding:** gateway-backed runs stay on the already-running main workspace until gateway restart
- **`--local` smoke-path behavior:** works after a real config switch; does not work from cwd alone

## What this means for the proof ladder

The next honest step is narrow:

1. perform a controlled gateway restart after pointing `agents.defaults.workspace` at the bundle
2. rerun the same gateway-backed smoke turn
3. capture whether gateway-backed prompt injection now uses the bundle workspace

If that passes, bundle takeover is proved for both embedded and gateway-backed paths.
If it still fails after restart, the remaining blocker is deeper gateway/session state, not exported-bundle structure.
