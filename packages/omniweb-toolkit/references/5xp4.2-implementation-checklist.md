# 5xp4.2 Implementation Checklist

This checklist translates the architecture notes into implementation work against the current repo.

The target is not a full redesign.
The target is to make the existing substrate/seam/skill split more explicit and less leaky.

---

# A. Contract work first

## A1. Add first-class intent-resolution types
- [ ] Create a new file for intent/result contracts near the runtime/seam layer.
  - likely: `src/intent-types.ts`
- [ ] Define input-side action intent types that are skill-safe.
  - `skip`
  - bounded action intent(s)
- [ ] Define resolution states:
  - `executable`
  - `blocked`
  - `supervised`
  - `unsupported`
- [ ] Define normalized fields on resolved intent:
  - action family
  - normalized target
  - normalized draft
  - reason codes
  - missing requirements
  - execution-path family
- [ ] Define normalized execution result shape.
- [ ] Define normalized verification/result-readback shape.

## A2. Extend readiness into resolution truth
- [ ] Audit `src/readiness.ts` for what already exists.
- [ ] Keep current capability checks intact.
- [ ] Add or wire resolution helpers so capability truth can feed resolved-intent truth.
- [ ] Make blocked vs unsupported vs supervised explicit instead of inferred ad hoc.

---

# B. Extract seam logic out of `minimal-agent.ts`

## B1. Isolate current responsibilities in `src/minimal-agent.ts`
- [ ] Mark which sections are pure orchestration.
- [ ] Mark which sections are actually readiness interpretation.
- [ ] Mark which sections are action-family execution routing.
- [ ] Mark which sections are supervision/support truth.
- [ ] Mark which sections are starter/skill policy leakage.

## B2. Create seam helpers below the agent layer
- [ ] Add a resolver module.
  - likely: `src/resolve-intent.ts`
- [ ] Add an execution module.
  - likely: `src/execute-intent.ts`
- [ ] Add a verification/result-readback module.
  - likely: `src/verify-intent-result.ts`
- [ ] Make these modules depend on runtime/seam primitives, not on skill files.

## B3. Shrink `minimal-agent.ts` to orchestration
- [ ] Keep:
  - observe-cycle sequencing
  - state transitions
  - persistence hooks
  - ledger writes
  - high-level call order
- [ ] Replace in-file execution branching with seam calls.
- [ ] Replace in-file readiness interpretation with resolved-intent calls.
- [ ] Replace in-file supervision/support determination with resolved-intent calls.
- [ ] Make the file boring.

---

# C. Clarify the seam around `hive.ts`

## C1. Audit `src/hive.ts`
- [ ] Separate methods that are pure convenience wrappers from methods that encode deeper operational mechanics.
- [ ] Mark any duplicated support truth that should instead come from resolved intent.
- [ ] Mark any policy assumptions that do not belong in a colony-facing convenience surface.

## C2. Keep `hive.ts` as the practical colony-facing API
- [ ] Preserve lazy session setup.
- [ ] Preserve typed error wrapping.
- [ ] Preserve broad consumer-usable API shape.

## C3. Stop making `hive.ts` carry hidden skill policy
- [ ] Ensure no topic/strategy heuristics are introduced here.
- [ ] Ensure evidence/source preference that is skill-specific is not treated as protocol substrate truth.

---

# D. Split generic attestation mechanics from policy

## D1. Audit `src/minimal-attestation-plan.ts`
- [ ] Identify generic candidate normalization logic.
- [ ] Identify preflight candidate shaping that is protocol-generic.
- [ ] Identify source-ranking or preference heuristics that are skill-specific.

## D2. Re-home policy if needed
- [ ] Keep generic evidence-path mechanics below the seam.
- [ ] Move topic- or skill-specific source preference upward into skill-local code/helpers.

# E. Shrink the public story of `src/agent.ts`

## E1. Audit current exports
- [ ] List exports that are truly generic agent runtime scaffolding.
- [ ] List exports that are research-specific.
- [ ] List exports that are market-specific.
- [ ] List exports that are engagement-specific.
- [ ] List legacy compatibility exports.

## E2. Define the intended `omniweb-toolkit/agent` surface
- [ ] Keep the minimal cycle/loop runtime exports.
- [ ] Keep session-ledger exports.
- [ ] Keep only a small set of generic starter/runtime helpers if they still earn their place.

## E3. Move or de-emphasize helper sprawl
- [ ] Move domain/helper clusters to narrower subpaths, or
- [ ] keep them internal/non-primary if a move is too disruptive right now.
- [ ] Stop making `agent.ts` the default umbrella for all accumulated helper families.

# F. Keep root substrate clean, but fill obvious read gaps

## F1. Audit root read substrate vs runtime convenience reads
- [ ] Compare `src/client.ts` / `src/read-types.ts` to read methods currently exposed only via `hive.ts`.
- [ ] Identify stable read contracts that belong at the root substrate.
- [ ] Identify unstable or runtime-heavy reads that should stay out of the root.

## F2. Extend root read substrate only where justified
- [ ] Add stable thread/post-detail read contracts if missing and root-safe.
- [ ] Add stable response types if they are generic enough to deserve root exposure.
- [ ] Do not pull runtime-heavy auth/session logic into the root package.

# J. Done criteria

`5xp4.2` is done when:
- [ ] a first-class resolved-intent contract exists below the skill layer
- [ ] `minimal-agent.ts` is mostly orchestration rather than execution truth
- [ ] `starter.ts` is visibly skill-local rather than semi-architectural
- [ ] `agent.ts` no longer serves as the default export pile for every historical helper family

# K. Non-goal reminder

Do not mistake cleanup theatre for progress.

Not required for `5xp4.2`:
- deleting all legacy helpers
- inventing a new grand architecture name
- rewriting the toolkit around a different abstraction just to feel cleaner
- broadening live-write claims

The point is to reduce leakage and clarify ownership, not to perform a stylish rewrite.
